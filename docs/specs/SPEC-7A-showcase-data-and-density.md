# SPEC-7A: Showcase Data and Layout Density

Feature:      A demo-data command that fills the database with believable
              fictional content (movies, posters, screens, showtimes, partly
              booked seat maps, a demo account), plus a layout pass so the user
              app looks like a finished product with no empty-looking screens
Priority:     P6 (Frontend, showcase)
Status:       See SPEC-7A.status — this line is for human reference only
Dependencies: SPEC-3 (catalog services), SPEC-4 (hold and confirm services),
              SPEC-5 (cancel), SPEC-7 (frontend pages, PROMPT 1-5 done)
Related Docs: SPEC-7, docs/design/frontend-design-brief.md, steering/*.md

---

## 1. Overview

SPEC-7 gives a working app on an empty database, which looks unfinished in a
portfolio. This SPEC adds:

1. A separate command `python -m src.db.seed_demo` (backend) that creates
   fictional but realistic content for the next 14 days, through the existing
   services so every business rule still holds.
2. Twelve original poster images (SVG) in the design-brief palette, served by
   the frontend.
3. A demo user and a few fictional guests, so seat maps show a believable mix of
   free and taken seats and "My reservations" is not empty.
4. A density pass on the Browse and Movie pages so wide screens do not show large
   empty areas.

No schema change, no new dependency, no change to any API. The command is never
run by the application and never by the test suite on a real database.

Out of scope: real film titles, real posters or any copyrighted material;
screenshots in the README (later); admin UI (SPEC-8).

## 2. Design

### 2.1 Decisions (need George's approval)

| # | Decision | Reason |
|---|---|---|
| D1 | Demo data comes from a separate command `src/db/seed_demo.py`, not from app startup or migrations | Production-like code paths stay clean; the data is optional |
| D2 | All titles, people and descriptions are fictional; posters are original abstract SVGs generated by a small Python tool (`tools/generate_posters.py`, no dependency) and committed to `frontend/public/posters/` | No copyright, works offline, matches the palette |
| D3 | `poster_url` is stored as an absolute URL built from `DEMO_POSTER_BASE_URL` (default `http://localhost:5173`) + `/posters/<file>.svg`. Cursor checks SPEC-3: if the backend accepts a relative path, it uses that and `DEMO_POSTER_BASE_URL` is not needed | The catalog validator may require http(s) |
| D4 | Data volume: 6 genres, 12 movies, 3 screens (8x12, 10x14, 6x10 seats), 4 slots per screen per day at 12:00, 15:00, 18:00, 21:00 cinema time, window today .. today+13 | Enough for a full-looking browse page and varied seat maps |
| D5 | Prices in cents: 12:00 = 1500, 15:00 = 2000, 18:00 = 2500, 21:00 = 2500; the third screen adds +500 | Realistic spread; currency comes from the frontend |
| D6 | Occupancy through the real services (hold then confirm) by fictional guest users: target share of seats taken 12:00 = 15%, 15:00 = 30%, 18:00 = 55%, 21:00 = 70%, each +-10 points; groups of 1-4 adjacent seats | A lively but not sold-out seat map |
| D7 | Demo user from `DEMO_USER_EMAIL` and `DEMO_USER_PASSWORD` in `.env` (no default password, nothing in code or docs). It gets two upcoming confirmed reservations and one cancelled one | "My reservations" looks used |
| D8 | The command is idempotent (a second run adds nothing) and deterministic (`random.Random(7)`); no reset option | Safe to re-run; to start over, recreate the dev database |
| D9 | The command refuses to run when the database name ends with `_test` | Protects the test database |
| D10 | Density: content max width 1200 px, centered; Browse movie blocks in two columns from 1024 px; Movie page is two columns from 768 px (poster 280 px left, details right); smaller vertical rhythm; skeletons match the final layout | No large empty areas on desktop, no layout jump |

### 2.2 Fictional catalog (fixed, used by the seed)

Genres: Drama, Thriller, Comedy, Sci-Fi, Documentary, Family.

Twelve movies (title, runtime in minutes, genres): The Long Quiet (112, Drama),
Harbour Lights (98, Drama), Paper Moons (104, Comedy, Family), Static Bloom
(121, Sci-Fi, Thriller), The Salt Road (133, Drama), Night Shift at Nine (95,
Comedy), Orbit of Small Things (108, Sci-Fi, Family), Glass Orchard (117,
Thriller), A Year in Tbilisi Rain (87, Documentary), Second Summer (101, Comedy,
Drama), Lantern Hill (126, Thriller), The Cartographer's Daughter (139, Drama).
Each has a 2-3 sentence original description. (Names are invented; if one
happens to match a real film, Cursor reports it and picks another.)

Assignment of movie to showtime is a pure function of (day offset, screen
index, slot index), so it is reproducible and every movie appears on several
days.

### 2.3 Behaviour of the command

1. Read settings (same `.env` as the app) and refuse (clear message, non-zero
   exit) when `DEMO_USER_EMAIL` or `DEMO_USER_PASSWORD` is missing or the
   database name ends with `_test`.
2. Ensure genres, movies, screens exist (matched by unique name/title).
3. For each day and slot not in the past, ensure the showtime exists.
4. For each showtime without any reservation yet, create the target occupancy.
5. Ensure the demo user and its three reservations exist.
6. Print a short summary: created counts and skipped counts.

Every step uses the existing services and rules. A step that finds its data
already present does nothing.

## 3. Requirements (EARS)

- **FR-1** When `seed_demo` runs on an empty catalog, the system shall create the
  genres, movies, screens and showtimes of Section 2.2 / D4, with prices of D5.
- **FR-2** The system shall create all data through the existing services, so
  the overlap rule, the unique active-seat index and the money rules hold.
- **FR-3** When `seed_demo` runs a second time, the system shall create nothing
  new and exit successfully.
- **FR-4** The system shall produce the same catalog and the same occupancy on
  every fresh run (fixed random seed).
- **FR-5** When `DEMO_USER_EMAIL` or `DEMO_USER_PASSWORD` is missing, or the
  database name ends with `_test`, the system shall stop before writing anything.
- **FR-6** The system shall not create a showtime that starts in the past.
- **FR-7** The system shall give each seeded movie a `poster_url` that points to
  one of twelve distinct committed SVG files.
- **FR-8** (UI) At widths of 1024 px and above, the Browse page shall show movie
  blocks in two columns inside a content area no wider than 1200 px; at widths
  below 1024 px, in one column.
- **FR-9** (UI) At widths of 768 px and above, the Movie page shall show the
  poster and details side by side.
- **FR-10** (UI) While data loads, the skeletons shall have the same outer
  layout as the loaded page.
- **FR-11** (UI) No change shall add horizontal scrolling at 390 px width.

## 5. Verification

### 5.1 Automated (backend, test database, committed connections, cleanup in
`finally`)

1. `seed_demo_creates_expected_catalog_counts` — 6 genres, 12 movies, 3 screens
   with 96, 140, 60 seats; showtimes only for future slots; every `poster_url`
   points to a file that exists in `frontend/public/posters/` and all 12 differ.
2. `seed_demo_is_idempotent_second_run_adds_nothing` — row counts of genres,
   movies, screens, showtimes, reservations, users are identical after run 2.
3. `seed_demo_respects_rules_after_seeding` — no two showtimes of one screen
   overlap by the slot rule; no showtime in the past; no seat has two active
   reservations; occupancy per slot lies inside its D6 range +-10 points.
4. `seed_demo_demo_user_has_three_reservations` — 2 confirmed upcoming, 1
   cancelled, all belonging to the demo user.
5. `seed_demo_refuses_test_database_name_and_missing_password` — both cases stop
   before any write (row counts unchanged) and report a clear error.

The existing 177 backend tests and 22 (now more) frontend tests stay green.

### 5.2 Equivalence classes and boundaries
- Window: day offset 0 (past slots skipped), 1, 13, 14 (not created).
- Occupancy target: 15%, 70% (+-10); never 0% and never 100%.
- Credentials: missing email, missing password, both present.

## Implementation Status

PROMPT 7A-1 (poster generator, posters, `seed_demo`, tests 1-5): done.
PROMPT 7A-2 (the frontend density pass, FR-8 to FR-11): not started, so
acceptance A5 to A8 are still open. A1 to A4 are the user's manual checks
against a running application; the command itself is exercised by the
automated tests below.

What exists:

- `tools/generate_posters.py` (repository root `tools/`, standard library
  only) writes the twelve SVGs to `frontend/public/posters/`, one per title of
  Section 2.2, named after the title's slug. The files are committed; neither
  the seed nor the tests depend on the generator.
- `backend/src/db/seed_demo.py` — `python -m src.db.seed_demo` creates the
  catalog (6 genres, 12 films with poster URLs, 3 screens and their seat maps),
  the 14-day showtime window with its prices, the guest occupancy through the
  real `hold` and `confirm` services, and the demo account's three
  reservations. The services never commit, so the whole run is one
  transaction; `main()` commits it, and a crash leaves nothing behind.
- `backend/tests/integration/test_seed_demo.py` — the five checks of Section
  5.1, sharing one seeding run (see the decisions below).

Decisions taken while implementing (recorded here, no spec change needed):

- **The three `DEMO_*` variables are read by the command, not by
  `src/core/config.py`.** D7 leaves this open ("read ONLY by this command, not
  in Settings", as `SEED_ADMIN_*` already works). Keeping them out of `Settings`
  means the application can start without them and that the refusal message can
  name the missing variable; `.env.example` documents all three next to
  `SEED_ADMIN_*`.
- **`DEMO_POSTER_BASE_URL` has a default, the credentials do not.** FR-5 makes a
  missing e-mail or password fatal, while the poster origin has one obvious
  development value (`http://localhost:5173`, the Vite server). Poster paths are
  stored absolute (`<base>/posters/<slug>.svg`) so the catalogue can point at any
  origin without a code change.
- **Occupancy is created by `hold` + `confirm`, one reservation per group**, so
  every seat passes the same conflict, expiry and status rules as a real
  booking (FR-2). The plan is driven by `random.Random(7)` and the group size
  draws one to four adjacent seats in a single row; a showtime that already has
  any reservation is skipped whole, which is what makes a second run a no-op.
- **The fill guarantees the D6 band, it does not merely aim at it.** The target
  is `math.ceil(seats * share)`, so rounding can never land below the band's
  floor, and when the drawn group size no longer fits in any row the fill falls
  back to the longest run that still does instead of stopping. Without those two
  rules the random fill occasionally finished one or two seats under the floor
  (the first hosted test run caught exactly that: 56 seats against a floor of
  57.6 on a 96-seat screen); a check over six random seeds now keeps the smallest
  margin at or above the floor on all 168 showtimes.
- **The tests seed once for all five checks.** The dataset is a few thousand
  rows produced through the services, so a module-scoped fixture deletes
  leftovers, seeds twice and hands both summaries to the tests; the second
  summary and the row counts around it are the idempotency evidence (test 2).
  Check 5 does not use the dataset at all -- it is about refusing to run.
- **The tests seed a two-day window, not the command's fortnight.** The whole
  plan runs through `seed_demo(..., days=...)`, a keyword argument that defaults
  to `_WINDOW_DAYS`; the tests pass `2`, so the shared seeding run books 24
  showtimes instead of 168 and finishes in minutes over the hosted database.
  Only the window is shortened: every screen, every slot, the occupancy band and
  the demo reservations are still exercised, and test 1 asserts both that the
  command's default is the D4 fortnight and that nothing exists on the day after
  the tests' window.
- **The test module's engine uses `NullPool`.** Every `asyncio.run` helper call
  drives its own event loop (a selector loop on Windows, like the command's
  `__main__`), and an async connection is bound to the loop that opened it, so
  pooling connections between calls would use them from the wrong loop.
- **The tests sign in with no real credential.** The demo e-mail and password
  they seed with are throwaway values under `example.invalid`; nothing in the
  tests or in `.env.example` carries the `.env` demo password.

Known limits (not blockers):

- One full run against the hosted database takes roughly 45 minutes, because
  the occupancy step is about 2 600 `hold` + `confirm` pairs -- some fifteen
  round trips each over a link with ~65 ms latency. A second run takes well
  under a minute (every step skips). Against a local PostgreSQL the command
  finishes in seconds. If the long run becomes a nuisance, the fix is fewer
  round trips inside the seed (batch the seat inserts), not a smaller dataset.
- The test module therefore avoids that wait: it seeds two days (see above), so
  `pytest tests -k seed_demo` spends a few minutes inside the module fixture with
  no output instead of the ~45 a full window would take. A test that needs the
  command's real fortnight has to call `seed_demo` without `days`.
- The hosted database is a Neon branch, and Neon can restart the compute between
  runs (`AdminShutdown: terminating connection due to administrator command`,
  every fixture erroring within seconds). Nothing is lost when that happens --
  the run is one transaction, so a restart rolls the seed back -- but the run has
  to be started again.
